Claude Observatory

Coding agents change code faster than anyone can read it, and a change accepted without being understood is a liability for you, not the agent's provider. The observatory is built for established and mission-critical codebases rather than throwaway prototypes: it records every edit a Claude Code session makes, through local hooks that cost no tokens. You review at the scope that fits the work, by several abstractions over what the agent changed for a given prompt. Every edit keeps its own diff and its own conflict-guarded undo, so reverting one leaves the others standing. When several agents work at once — subagents, workflow runs, sessions in parallel git worktrees — their work does not blur together: every edit is correlated back to the agent that made it. Everything stays local and git-free, and one store serves the terminal, VS Code, and JetBrains IDEs.

The gap

Interpretability at crunch time

A backlog of changes reviewed at the end of an agent's session creates a bottleneck, moving the work of verifying and evaluating every change onto the reviewer at once, after the context that produced them is gone. Existing tools address parts of the problem: usage meters count tokens, log viewers replay a session, editor assistants and Claude Code's own /rewind roll back to a checkpoint, and orchestrators launch fleets of agents and present each branch as one diff to merge. A checkpoint is coarse — it reverts a whole turn rather than one edit, does not track the files a shell command changed, and clears when the session ends. The observatory records each edit instead, tracing each action back to the chain of thought the model recorded for it.

What sets it apart

From one edit to the whole trace

  • The record is built outside the model loop. Capture runs in local hooks: it costs no tokens and changes nothing about what the agent sees or the decisions it makes. The record builds itself as the agent works, so it exists before you need it rather than being reconstructed once the context is gone. Everything stays on your machine; nothing is sent anywhere.
  • Any edit can be reversed on its own. A position-anchored merge removes one change while the edits around it stay in place. When a later edit genuinely overlaps, the undo is refused rather than applied blindly: no clean git state is required, and nothing is silently overwritten.
  • Review follows the unit of work. The edits one prompt produced read as one sequence, in the order the agent made them, across files; the same review scales down to a single edit or up to a task or a workflow run. Single edits give precision; sequences give the shape of the work.
  • Every edit is recorded. Each text change is saved the moment the agent makes it, including the files a shell command changed. When a named file cannot be snapshotted — a binary, or one past the size cap — the record marks it an explicit skip rather than dropping it quietly. The shell walk is bounded: it skips vendor and build directories and stops at a file-count cap, so changes beneath those are not captured at all.
  • Every surface reads one store. VS Code, JetBrains IDEs, and the terminal share the same local record, so review does not depend on a particular editor or on an outside service.
  • Every tool call is explained. The transcript the session already produced yields Claude's reasoning, a timeline of each tool call, flags on risky shell commands, and the two audits: the edits and reads that landed outside the workspace, and everywhere the session reached off the machine.
  • Many agents appear in one view. When several agents run in parallel across git worktrees, the observatory unifies them: who is working, on what, and where their changes conflict.

Overview

Every agent and its changes in one panel

The Overview is a master-detail panel. Its left nav has five tabs, led by Sessions, this workspace's recorded sessions — the one tab whose selection switches what the whole observatory reviews. Then Fleet, every running agent across the repository's worktrees; Workflows, every multi-agent run; Tasks, the session's numbered task list; and Processes, the background shells it launched. Fleet and Workflows rows show a live phase and an activity sparkline, and an interrupted run that never recorded completion is not shown as running. Selecting a row fills the right side with its change map, two labeled sections top to bottom: Folders, a strip of equal tiles, one per changed directory, ranked by lines changed and colored by review status; and Files, a churn-ranked ledger of every changed file. Clicking a Folder tile steps the nav bar's Folder axis to that folder's first pending edit; clicking a file opens its diff. A summary bar reports the pending, accepted, and reverted counts for whatever is in scope and names the picked prompt or folder filter; beneath it, the selected row's feed shows what that thing is doing.

The fleet

Parallel agents across worktrees

Every running Claude session appears in one live board, including sessions in separate git worktrees of one repository, correlated without the git binary. Each row carries a live phase (working · awaiting-input · awaiting-permission · idle · done, with heuristic phases marked ~), its worktree and branch, a sparkline, ±lines, tokens · time, and risk; live file conflicts in the Actions view flag any file two agents are touching. Tracking is path-only, at zero tokens.

Sessions

Every session in the workspace, newest conversation first

The Sessions tab lists each Claude Code session recorded for this workspace, led by Claude's own title for it and ordered by when its conversation was last active. Selecting a row switches what every window reviews, so a session you left yesterday is one click away. The listing is built from directory stats and cached titles rather than from the sessions' edit logs, which is why it opens at once however many edits have accumulated. For moving between conversations that are both still running, the Timeline carries its own selector above the Prompts list, listing only the sessions still active plus the one under review; picking one switches the whole observatory, and this tab stays the full list. The Overview's left nav can also pair its related sections side by side — Sessions beside Fleet, Workflows beside Tasks and Processes — since which conversation and who is working in it are one question.

Inline review

Review directly in the editor

Claude's pending edits appear in the editor itself: a tinted line, a gutter star, removed lines as ghost text in both editors, and a per-edit lens that names the edit, its churn and its position, then carries Keep, Undo, Chat, the diff, and the way through to the fuller review surface. Resolving one edit carries you to the next awaiting review, crossing into another file when that is where it is. A file with edits awaiting review carries their count as a badge in the editor's own project tree, and on the editor tab in VS Code.

Per-edit diffs

A dedicated diff for each edit

Every entry opens as its own diff rather than one session-wide diff to untangle.

Surgical undo & file history

Surgical undo

A single change can be reverted without touching later edits, and File History lists every revision a file has been through.

Observations

A change feed with Claude's reasoning

The session appears as a feed of files ordered by most-recent activity; adjacent edits to the same file coalesce into one ×N run. Each entry is paired with Claude's reasoning, parsed from the transcript it already wrote, at zero extra tokens. Above the feed, a Context section names what shaped the session — skills invoked, plans written, memory read, whether it resumed from a compaction — each row marked with whether the transcript proves it or the file is merely present where Claude Code loads it.

Prompts

The session, as the conversation you had

Every other view organizes the work the way the agent saw it: worktrees, runs, its own plan, files. The Prompts window is one row per thing you asked for, in order, each with its own counts — edits, files, folders, tokens, subagents, workflow runs, tasks, and shells. The prompt is printed whole, wrapped rather than clipped, and each row expands to show Claude's reply to it. Selecting a row scopes the Overview beside it: the fleet, the runs, the tasks, the shells, and the entire change map narrow to the work that prompt caused, and the review actions retarget to it. Work belongs to the prompt that started it, not the one that was current when it finished.

Processes

Background shells, after they leave the screen

Shells started with run_in_background appear as their own tab, each row showing its state, how long it has run, and how much output it produced; running shells sort first. Selecting one shows its full command and a tail of that output. Shell ids are the harness's own — a transcript records no OS process id, and the agent may be running over SSH or in a devcontainer, so inferring one by scanning local processes would be wrong.

Live feed

What one thing is doing, read from what it writes

Selecting an agent, a workflow, a task, a process, or the session itself shows its activity, read from the file that thing writes. While the source is still writing, the feed is followed live and stamped with how long ago it last moved — the age of the newest evidence, not a claim of real time. Once the source has finished, the same view becomes an audit log, a record rather than a stream, and polling stops. Entries read oldest first, and a capped feed states how many earlier ones it did not show.

Risk & egress

Risk and egress audits

Risk flags the shell commands that were destructive or privileged, and reports the edits that landed outside the workspace. Egress lists everywhere the session reached off the machine, and the files it read from outside the workspace — each destination scoped remote, outside, or unknown, because a local path that left the workspace is a fact and an unclassifiable destination is an admission. Both report what was exercised, never what was permitted: approval prompts are never written to the transcript.

Chat handoff

Context-preloaded chat prompts

One click assembles the before/after diff, Claude's reasoning, and the command and its result into a ready-to-paste prompt on your clipboard, for your own Claude session. The observatory never calls a model, so this costs zero extra tokens.

Stats

Progress, tokens, and usage

The session's cumulative tokens — input, output, cached, and the cache hit rate — sit under its name, which also carries the model and effort level the session runs on and, when the harness has compacted the conversation, how many times and how much the last compaction dropped. Below them sit a live scoreboard of pending, accepted, and reverted edits; token plots by time window; and context and plan usage. The session is identified by name rather than by its raw id, and the 5-hour and weekly usage rows show an estimated used-of-total figure, inferred from the tokens spent divided by the percentage reported.

Navigation bar

Review controls on four surfaces

One review bar appears on four surfaces: the status bar, the editor's title bar, a floating bar over the live edit, and the Overview panel. On the Overview it opens as two rows. The top row holds the session controls: the name of the session under review — its title or first prompt, with the raw id in the tooltip, and a label rather than a control, since the Sessions tab is where the session changes — then the session-wide Accept All, Reject All, Clear Resolved, and Export actions, and, on the right, Search, Active only, Spotlight, and Refresh. The bottom row holds four review axes that step the pending edits at four granularities. The Diff axis steps the open file's edits and carries Keep, Undo, Chat, and View diff, which opens a real side-by-side diff editor. The File axis steps changed files with Accept File and Reject File; the Folder axis steps changed directories, acting on only that folder's edits. The Prompt axis steps your own prompts, showing each one's file and edit totals with Review, Accept Prompt, Reject Prompt, and Rewind — which reverts every unreviewed edit from that ask onward, not just its own.

In the editor

The review bar where you are reading

Each editor carries the controls into the file itself, in the form its API allows. JetBrains IDEs get a floating toolbar on the platform's own floating-toolbar layer while the open file has edits awaiting review — Keep, Undo, Chat, View diff, the Diff counter and its steppers, Accept and Reject File, Spotlight, and Clear Resolved — and a setting chooses the bar, the notification banner it replaces, both, or neither.

VS Code exposes no floating-widget API to extensions, and that has not changed: an extension cannot draw an overlay widget, and a comment thread is the only interactive surface that can float over code. What it now has is a compact bar built on exactly that surface — a single row of Keep, Undo, the edit and file steppers, Diff and Details, under a live title naming the edit, its churn and its position on both axes. The full review bubble, with Claude's reasoning and the diff in git's colors, is the same widget in its other form, one click away on Details and back again on Collapse. The setting is spelled the same in both editors and means the same thing where they overlap. Keeping or reverting one edit opens the next one still awaiting review, crossing into another file when that is where it is; bulk actions and redo never move you.

Install

One-command install

Install once, run Claude Code, and every edit is captured for review.

$curl -fsSL https://raw.githubusercontent.com/cell-observatory/claude-observatory/main/scripts/bootstrap.sh | bash

macOS and Linux — and Windows from Git Bash.

PS>irm https://raw.githubusercontent.com/cell-observatory/claude-observatory/main/install.ps1 | iex

Windows, native PowerShell — no bash, no WSL. Either one installs the CLI and then the extensions for whatever editors are on the machine (VS Code family and/or JetBrains). To follow the rolling pre-release, a piped script needs its arguments passed through: append -s -- --channel dev to the bash line, or run the PowerShell one as & ([scriptblock]::Create((irm <url>))) -Channel dev. On Windows the bundled status line is the one part that still needs Git Bash and jq — everything else runs natively.

Then look around with no Claude session at all: Claude Observatory: Start Demo Mode from the VS Code command palette or JetBrains Find Action, or claude-observatory demo in the terminal. It replays a real session through the real capture pipeline and walks you through every panel; leaving removes every trace.

Paste this into a Claude Code session to install everything.

Install Claude Observatory for me — run its bootstrap installer, then `claude-observatory doctor`. The capture hooks only take effect on a fresh session, so afterward have me quit, run `claude-observatory init` in a plain terminal, and relaunch.

To update an existing install, re-run the command above or run claude-observatory update — it refreshes the CLI and both editor extensions (add --check to preview). Each editor can also self-update: VS Code offers a one-click Update now, and JetBrains auto-updates once you add the plugin repository. There are two release channels — stable, and a rolling pre-release of the dev branch — switchable from the version chip on the Overview toolbar or with claude-observatory update --channel dev.
