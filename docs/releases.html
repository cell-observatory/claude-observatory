Releases & channels

Claude Observatory ships on two release channels. Stable is the default: tagged releases, cut when the work has soaked. Pre-release is a rolling build of the development branch, republished on every push, for anyone who wants what is being built as it is built. Every install follows exactly one channel, and switching is one action from either editor or one command from the terminal.

The two channels

Stable and Pre-release

Stable

Current stable: v0.9.3 · current pre-release: rolling — read live from the releases feed (the static value is the fallback from this page’s last deploy). Every release’s changes: the full changelog.

Tagged releases, cut from main. Each one is a version like v0.9.0: the full three-OS test matrix and the end-to-end suite ran on the exact commit, the artifacts (CLI tarball, VS Code .vsix, JetBrains plugin zip) are attached to the GitHub Release, and the changelog names what changed. This is the default channel — releases/latest serves it, and nothing on it ever moves after it is published.

Pre-release

A rolling build of the dev branch. Every push to dev rebuilds all the artifacts, stamps them <next>-dev.<n> (for example 0.10.0-dev.37), and refreshes one GitHub release — tag dev-latest, marked prerelease, so the stable channel never sees it. You get merged features and fixes days or weeks before they reach a tagged release, with correspondingly less soak time. The version ordering is real semver: every dev build is newer than the stable it forked from, and the eventual tagged release is newer than every dev build that led to it — so promotion lands as an ordinary update.

Switching & updating

One chip in the editors, one flag in the terminal

Both editors pin a version chip at the right edge of the Overview's toolbar. It shows the version you are running; when the channel you follow has something newer, a dot appears. Its menu holds everything this page describes:

Update now

Always in the menu. Installs the newest release of the channel you follow — the CLI, both editor plugins, and the bundled status line, all in one pass — then offers the reload (VS Code) or restart (JetBrains) that loads it. When nothing is newer it says so and installs nothing; clicking it also re-checks the release feed.

Stable ⇄ Pre-release

Switching persists the choice and installs the target channel's newest immediately — including the deliberate downgrade when you leave the pre-release channel for stable. Updates follow the chosen channel from then on: the CLI's once-a-day nudge, VS Code's background check, and the chip itself all compare against it.

The terminal equivalents

$ claude-observatory update --check
channel: stable
CLI: up to date (0.9.0)
…one row per installed editor plugin…
pre-release channel: 0.10.0-dev.37 — switch with `claude-observatory update --channel dev`
run `claude-observatory update` to apply.

$ claude-observatory update --channel dev
✓ switched to the pre-release (dev) channel
downloading claude-observatory-cli-dev.tgz …
✓ updated the CLI 0.9.0 → 0.10.0-dev.37
…the editor plugins and the status line refresh the same way…

$ claude-observatory update --channel stable   # back, any time

claude-observatory version --check reports the installed version, the followed channel, and both channels' newest at any time. The channel itself is one word in ~/.claude/claude-observatory/channel — no other state.

JetBrains IDE-native updates, per channel

The self-hosted plugin repository exists for both channels. Subscribe the IDE to exactly one (Settings → Plugins → ⚙ → Manage Plugin Repositories):

…/releases/latest/download/updatePlugins.xml — stable
…/releases/download/dev-latest/updatePlugins.xml — pre-release

(The chip's switch already covers the plugin; the repository URL is for IDE-native auto-updates.)

How a change ships

From a branch to your editor

One path, three stations — each PR runs the full three-OS test matrix before it can land anywhere:

feature / fix branch ──PR──▶ dev (pre-release channel) ──PR──▶ main (stable channel, tagged releases)

Landing on dev

Feature and fix PRs target the persistent dev branch. The moment one merges, the rolling pre-release rebuilds — anyone on the pre-release channel is one Update now away from it.

Promoting to main

When dev has soaked, a single dev → main PR promotes everything, and a version tag on the merge cuts the official release. Stable users see one coherent update with a changelog; pre-release users see the same content arrive as an ordinary (slightly newer) version.

Hotfixes

A critical fix that cannot wait for the next promote ships as a patch release cherry-picked from dev onto the stable line (v0.9.0 → v0.9.1). Stable users get it immediately; pre-release users already carry it — their rolling builds outrank the patch, so nothing downgrades.

The contributor-side details — workflows, version stamping, what to bump after a promote — live in CONTRIBUTING.

Contributing a change

One standardized path, and your feature ships the same hour

Every change — a maintainer's or a first-time contributor's — takes the same road:

1 · Branch and open a PR against dev

Fork (or branch), build the change, open a pull request with dev as the base. GitHub preselects main — switch it; a maintainer retargets any PR that misses this. The PR template carries the two things every change answers: the cross-editor parity checklist (features ship in the CLI, VS Code, and JetBrains, with shared logic in core exposed over --json) and a "tested on" line.

2 · Say what changed, where users will read it

Add one line under ## [Unreleased] in CHANGELOG.md as part of the PR. A promote renames that section to the release version — your words ship with the release that carries your work. User-facing changes update the docs and screenshots they touch, in the same PR.

3 · The gauntlet runs itself

Every PR gets the full three-OS test matrix, both editor builds, and CodeQL — regardless of where it came from. Fork PRs run with a read-only token, and nothing can publish from a PR: the release machinery only fires after a maintainer merges.

4 · Merged means installable

The merge push republishes the rolling pre-release within minutes. claude-observatory update --channel dev — or the version chip in either editor — and you are running your own feature the same hour. The stable channel picks it up with the next promote, batched and changelogged.

The full contributor guide — repo layout, the worked end-to-end example, the build & test cheat-sheet — is CONTRIBUTING.
